交付与接入：换一个权重，换回来也是一个动作

前三课回答「它凭什么值得信」。这一课回答团队真正会问的那句：这东西怎么到我手上，装上去会发生什么，装错了怎么退回来。

约 15 分钟 宿主坐标复核于 2026-10-14（tokencamp-pro HEAD 6b03be5） 配套：交付速查 · 术语表 · 课程目录

01替换的实质：只换一个权重文件

refine 是两段式：先 compress（抽取式删词，我们的 checkpoint，2–3 毫秒），再 rewrite（网关大模型回调）。「Leia 完成后能替换 refine 吗」这句话里的「替换」，指的只是第一段。换 compress 阶段的 checkpoint 权重——没有别的含义。

这不是口头约定，是接口形状决定的。宿主里加载压缩模型的地方只有一处：

# sidecars/refine/compressor.py:16
MODEL_ID = os.environ.get(
    "COMPRESSION_MODEL_ID",
    "microsoft/llmlingua-2-bert-base-multilingual-cased-meetingbank",
)

整个 Compressor 的构造就三件事：拿 MODEL_ID 加载 tokenizer 与 token 分类模型、记下自己的身份标签、放到设备上。谁被加载，由这一个常量决定。

换权重时不动的四样东西

  1. rewrite 阶段（网关 LLM 回调与它的两道 guardrail）——原样；
  2. /refine 协议与 x-tc-refine* 请求头语义——原样；
  3. fail-open（任何一环出问题就放行原文，绝不阻断请求）与 light mode——原样；
  4. 缓存、超时、隐私边界——原样。

收益与风险同边界。宿主 RefineTier 的默认值是 Off（settings.rs:77-80，transform.rs:241 直接 return）。压缩默认就是关着的：只有显式启用 rewrite_compress 档的工作区会走到我们的模型。所以换权重的价值上限 = 这批工作区的节省；换了之后出问题，影响面也正好是同一批。

这句话值得记住，因为它同时定了两件事：验收要对准的那批流量，和出事时的爆炸半径。二者是同一批。

02产物包五件：缺一不算交付

交付单元不是「一个模型文件」，是产物包。五件里少任何一件，都不叫交付——因为剩下四件都答不了收件人的问题。

件回答的问题怎么来的
checkpoint跑的是什么东西训练产物，须过 delivery verify
溯源 model card数据从哪来、许可干不干净手写 + 冻结 manifest 锚定（第三课）
对照报告凭什么说更好冻结考卷 149 条上的验收数字
延迟档案会不会拖慢线上阶段 1 双基线顺带产出；延迟闸 p95 ≤ 现网 1.2×
接入包我具体要改哪儿、怎么退leia delivery pack 从草案渲染

第五件是 2026-09-11 补上的，理由是前四件合起来仍然只说明「这东西不错」，没说明「你怎么用上它」——而团队实际卡住的往往是后者。接入包不是说明书，它是让宿主照做即可接入的单元：契约校验清单 + 宿主改动 patch + 切换/观察/回滚 runbook + 非差异清单（明确列出「切换后不变的东西」，省掉收件人自己推演）。

03drop-in 契约：四条，每条对着宿主的一行代码

「能替换」不是形容词，是四条可执行的硬条件。任何一条不满足，就不是替换权重，而是要宿主改代码——那件事的性质完全不同（跨仓、要排期、要说服）。

条件宿主哪里依赖它不满足的后果
architectures 含 BertForTokenClassification，num_labels == 2，id2label = {0: drop, 1: keep} 宿主把 softmax(logits)[..., 1] 当保留概率——位置语义，不是按名字找 写反了会静默反向：能加载、不报错、压缩照跑，只是留下该删的
tokenizer 必须是 fast（return_offsets_mapping 可用） 强制保留（force-keep）靠 offsets 把数字事实的字符区间映射到 token 没有 offsets，事实保护直接失效——而这正是现网最在意的那类丢失
模型类暴露 .bert 属性 refiner.py:338 的相似度 guardrail 直接调 self.compressor.model.bert(**inputs) 属性名不对就抛异常，请求回落到原文：不报错，但也白干
与现网同架构基底（mBERT-base 系列） 延迟档案与内存占用要能直接对比 延迟闸失去可比性——「慢了 1.2 倍」这句话就不再成立

前三条是运行时硬条件：不满足，host 要么跑不起来，要么跑错。第四条不是运行时条件，而是让「延迟可比」成立的前提——它的作用是保住延迟闸。分清楚这个差别，遇到「换个更大的底座行不行」时就知道该吵哪一条。

真实的反例

XLM-R-large 在公开基线上压缩更保守、fact recall 全档 1.0000——看上去是个更好的模型。它不是 drop-in：属性叫 .roberta，第三条不满足。后果很硬：阶段 1 的「后手牌」激活判据据此修订，这个升级点没被激活（另有延迟 p95 17.8–25.8 s 的账）。接入面能一票否决一个更好的模型——这就是为什么契约要写在最前面。

XLM-R-large 为什么不算 drop-in？

是属性名。延迟是它没被激活的另一笔账，不是 drop-in 契约的那一条——两条理由别混着说。

04契约是可执行的门：两层、三种判定

清单写在文档里就只是清单；变成命令才是门。本仓的 leia delivery verify <checkpoint 目录> 把四条拆成七个检查，分两层跑：

  • 静态层（5 项，默认依赖即可）。读 config.json 判架构类、标签数、标签语义；读 tokenizer.json 判是不是 fast、能不能给出可用的 offsets。不装 torch 也能跑。
  • 加载层（2 项，需要重依赖）。真的 from_pretrained 实例化一遍，断言模型确实有 .bert、运行时 tokenizer 确实给得出 offsets。装依赖：uv sync --group load。

判定有三种，不是两种：PASS / VIOLATION / UNVERIFIED。UNVERIFIED 永远不算 PASS——它只说实话「这次没证明」。这个区分不是洁癖：交付记录里必须能指出哪一次是双层 PASS，否则「验过了」就是一句空话。

$ leia delivery verify runs/train/pilot-v1/checkpoint
checkpoint: runs/train/pilot-v1/checkpoint (digest 8c35908db52f…, 6 files)
static layer: PASS (5/5 checks)
  architecture_class: PASS — architectures = ['BertForTokenClassification']
  num_labels: PASS — num_labels = 2 (id2label has 2 entries)
  id2label_semantics: PASS — id2label = {0: 'drop', 1: 'keep'}
  fast_tokenizer: PASS — tokenizer.json loads with the fast-tokenizer library
  offsets_available: PASS — probe encodes to 12 tokens, 12 non-degenerate offset spans
load layer: UNVERIFIED — transformers/torch not installed — enable with `uv sync --group load`
overall: PASS

上面是今天在这台机器、默认虚拟环境里的真实输出：静态层 5/5，加载层因为没装 torch 而 UNVERIFIED。换到装了 torch 的环境跑同一份 checkpoint，加载层变成 PASS 并多出两行（is_fast=True, 14 offset spans；model type BertForTokenClassification exposes `.bert`）。同一份产物、同一份代码，判定不同——差别只在环境。这就是为什么交付时要把报告冻在归档里。

下面这台机器让你亲手弄坏一处，看判定怎么动。开关是编的，它们代表的导出失误是真的：

报告的另一个性质是确定性：序列化时键排序、不写时间戳，同一份 checkpoint 在任何机器上验出同一串字节（加载层那一栏除外，它取决于环境）。审计「这份产物和上次那份是不是同一份」时，比的是这个 digest，不是文件夹名。

05接入包：让宿主照做即可

第五件产物由 leia delivery pack 生成，输出三件东西：

文件内容
SHA256SUMS逐文件哈希，shasum -a 256 -c 可直接校验——快照落盘后的第一件事
integration-pack.md由仓内草案 docs/delivery/refine-integration.md 渲染而成：占位符换成真实值，零手工填入
verify-report.json打包那一刻的机读校验报告

pack 的三条不可谈判性质

  1. verify 不过就不许打包。门在打包之前，不在之后——一个违反契约的 checkpoint 连产物包都出不来。
  2. 不覆盖已存在的输出目录。pack 是不可变产物；重打必须换新路径。
  3. 确定性 + 拒绝半渲染。草案里出现渲染器认不出的占位符，直接中止报错，绝不允许一个 {{…}} 漏进定稿。

第 3 条值得多看一眼：如果接入包里留着没替换的占位符，宿主会照着 {{MODEL_TAG}} 去改代码——这种错一定要在源头炸掉，而不是留给人眼在评审时发现。

还有一个渲染细节值得先知道：MODEL_ID 取 config.json 的 _name_or_path，缺该字段就退回目录名；MODEL_TAG 再取它的 basename。也就是说暂存目录名会被直接写进 patch 与宿主的指标标签。2026-10-14 实测：pilot 产物正好缺这个字段，渲染出的标签是 checkpoint，注入路径会变成 models/checkpoint。交付前把暂存目录命名为 leia-v1，或在导出时写入 _name_or_path。

传输与回滚素材是一件事。走私有 HF 仓下载到目标机，落成本地快照 + 逐文件哈希清单；此后运行时不再依赖 HF 的可达性与凭据。旧快照目录原地不删——它本身就是回滚素材。断网能启动、旧版本还在，这两条一起构成了「回滚是个动作，不是一个项目」。

06供货：触发式，不是一次性

Leia 与 refine 的关系定位是供货：交付自包含的产物（权重快照），既不是代码依赖，也不是一个服务。既然是供货，就要说清「什么时候再供一次」——四个触发器，无触发不交付：

  1. 真链路回归跌破验收线。换权重或影响压缩面的改动之后，必须跑真链路全量（149 条 ≈ 600 次网关调用），结果摘录入本仓归档。
  2. 负载分布漂移。操作化为 golden 主动扩集 + 线上聚合指标（节省率 / fallback / 延迟）的漂移告警。注意措辞：这些是代理信号，不声称测质量——客户 prompt 不能用于评测（第三课的红线二）。
  3. 训练语料的许可发生变化。许可链断了，产物就不能再供。
  4. v2（query-aware）作为独立能力线立项。它换的不只是权重，还有接口，属于另一次交付。

还有一条容易被忽略但很重要的性质：断供不等于断服务。产物自包含（本地快照 + 旧模型并存，from_pretrained(本地路径) 离线可跑），所以 Leia 项目停下来，不影响 refine 的运行与回滚。这正是「交付物供货」优于「代码依赖」的地方——依赖会腐烂，快照不会。

哪些属于「再交付」的触发器？（选出所有正确项）

没有日历这一条。供货由触发驱动，不由节奏驱动——「无触发不交付」正是为了避免为了交付而交付。

07切换与回滚：一条八步的 runbook

切换手册的价值在于把「看起来生效了」和「确实生效了」分开。压缩默认关闭、fail-open 又会把故障都吞掉，所以「没报错」什么都证明不了。步骤顺序就是为此排的：

  1. 落盘快照并校验哈希。同时跑 leia delivery verify 过契约。
  2. 打接入包里的 patch。改动被刻意限制在很少的几处，其余文件一行不动。
  3. 冷启动 sidecar，然后 GET /health。{"status":"ok","compressor":true} 才继续；false 意味着 light mode（只有 rewrite 在跑），停下来查。
  4. stub 冒烟。本仓的 fixture 配置，零网络零花费，验的是接线不是质量。
  5. 真链路回归。冻结考卷全量，走宿主网关账本——这是唯一能回答「质量掉没掉」的一步。
  6. 核判据，再切换。判据是：任务级质量 delta 的 95% 置信区间下界 ≥ 0，且压缩率或 fact recall 有一项显著提升。持平 = 不替换——负结果归档，refine 继续用公开 checkpoint。
  7. 观察。applied / fallback / skipped 计数 + 按压缩机标签分组的 token 节省指标。
  8. 回滚 = git revert + 重启。旧快照还在原地。

回滚不残留脏缓存。因为缓存键里含压缩机身份：换过权重之后，旧模型算出来的条目 key 不一样，自然失效。这不是巧合——它原本是一个真实的坑（键里不含压缩模型时，换完权重旧结果会静默继续命中，看起来切了、实际没切），现在被堵死了。

真链路回归跑完，质量 delta 的 CI 下界恰好是 0，压缩率也没提升。怎么办？

持平即停。判据里「下界 ≥ 0 且有一项显著提升」是一个合取——只满足前半句是没赢。改判据是最危险的那个选项：考卷跟着学生改，验收就作废了。

09收尾：三句话

记住这三句就够用

  1. 替换 = 只换 compress 阶段的权重。rewrite、协议、头、fail-open、guardrail 全不动；影响面 = 显式开了压缩的那些工作区。
  2. 契约四条是四行代码，不是一个形容词。标签语义、fast tokenizer、.bert、同架构基底——每条都能指到宿主的一行；leia delivery verify 把它变成两层七项、三种判定的可执行门。
  3. 持平 = 不替换；断供 ≠ 断服务。验收判据是合取（CI 下界 ≥ 0 且有一项显著提升）；产物自包含，Leia 停下来不影响 refine 继续跑、回滚。

不看上文，写一遍

同事（宿主侧的工程师）问你：「Leia 做完之后，refine 那边要改什么？」用四句话回答。其中一句必须提到回滚，还有一句必须提到你怎么证明切换成功了。

1. 改动面很小，而且不动语义。只换 compress 阶段的 checkpoint 权重——rewrite 阶段、/refine 协议、x-tc-refine* 头、fail-open 与 guardrail 一律不变；影响面限于显式启用压缩档的工作区（默认是关的）。
2. 换的是本地产物，不是远程依赖。权重走私有 HF 仓传到目标机、落成本地快照 + 逐文件 sha256，运行时不再依赖 HF 可达性与凭据。
3. 回滚 = git revert + 重启，旧快照原地保留。因为缓存键里含压缩机身份，换过权重之后旧模型算出的条目自然失效——回滚不会残留脏缓存。这也意味着断供不影响 refine 运行与回滚。
4. 证明分两步，缺一不可。先冷启动后 GET /health 看 compressor: true（false 是 light mode，不能继续）；再跑真链路回归对冻结考卷（149 条 ≈ 600 次网关调用），核判据：质量 delta 的 95% CI 下界 ≥ 0 且压缩率或 fact recall 有一项显著提升——持平就不切。切换后看按压缩机标签分组的 token 节省指标来观察。

  • src/leia/delivery.py 的模块 docstring — 七项检查与三种判定的最紧凑表述，五分钟读完，比任何二手转述都准。
