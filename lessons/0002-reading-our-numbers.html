怎么读我们的数字

Beam 报告里的每个数字都带着口径：谁数的、跟谁比、凭什么判。读错口径，同一份数据能得出相反的结论。这一课给你一副眼镜。

约 15 分钟 全部数字来自冻结全量 2026-09-12（149 条考卷，双 checkpoint） 配套：读表五问 · 第 01 课

01先有尺，才有「更好」

这个项目从第一天就把顺序定死了：先造尺，再谈优劣。立项本身不需要门槛（已经说了做），但任何「微调后更好」的说法，必须落在同一把尺上才算数——没有尺，不许声称赢。

这把尺由三样东西钉住，缺一样，数字就不可比：

  • 考卷：149 条冻结 golden（RAG 49 / system 50 / 对话 50），内容寻址 sha256 fb728d6a5042…。冻结纪律是「只许扩集重跑，不许改题」——考卷跟着学生改，验收就作废。
  • 钉子：作答模型 deepseek/deepseek-v4-pro、judge zhipu/glm-5.1、rubric v1（全文哈希进报告）、harness commit。换任何一根钉子，数字就换了一把尺。
  • 判据：任务级质量差值的 95% 置信区间下界不为负。第 4 节专门讲它为什么长这样。

02同一个东西，两个数字

「压缩率 29%」这句话本身是不完整的。同一批压缩结果，报告里同时给出两个口径：

口径数什么档位 0.2回答的问题
计费口径tiktoken cl100k_base0.2948客户账单会省多少
原生口径模型自己的 tokenizer（WordPiece）0.3017模型视野里删掉了多少

两个数字差 0.7 个百分点——不算大，但足以让「提升了 0.5 个点」这种结论变成假结论。更麻烦的是：这个差值的方向会随模型翻转。同一个档位下，XLM-R-large 的计费口径是 0.2097、原生口径是 0.1941——原生比计费还低。换基底模型就换 tokenizer，换 tokenizer 就换两套数字的关系。

第三条口径坑：fact recall 是字符串逐字判定（"#A-1029" in 压缩文本）。而压缩输出的字符串会被解码重排——第 01 课实测过：WordPiece 把 #A-1029 解成 # A - 1029。所以这个指标测的其实是「字符串相邻关系有没有被破坏」，不只是「事实有没有被删」。

报告里同时出现 0.2948 与 0.3017 两个压缩率，原因是什么？

03四个指标，各管一件事

指标回答的问题它怎么骗人
压缩率省了多少省得多不等于答得对
fact recall数字、编号活下来了吗字符串级判定，会受解码空格影响
token F0.5压缩后还像不像原文保留得越多它越高，与任务质量无关
任务级质量 delta下游答案变好还是变差样本量小就会给出假区间（见第 4 节）

前三个是代理指标——它们便宜、可自动化、不需要真跑下游任务；最后一个是主指标，也是唯一进验收判据的。为什么要这么分？看真实数据：

档位压缩率 ↑fact recalltoken F0.5 ↓任务质量 delta [95% CI]
0.10.22030.76990.6965+0.0095 [−0.0140, +0.0345]
0.20.29480.76990.6626+0.0009 [−0.0330, +0.0363]
0.30.35900.76990.6393−0.0151 [−0.0507, +0.0209]
0.40.41790.76990.6159−0.0670 [−0.1075, −0.0279]
0.50.47480.76990.5883−0.0729 [−0.1172, −0.0293]

从 0.3 走到 0.5：压缩率涨了 12 个百分点（好看），fact recall 一动不动（因为事实被正则钉死），token F0.5 一路下滑（像不像原文越来越差），而任务质量已经变成确定的负值——0.4 与 0.5 档的区间整段落在 0 以下。

换个模型这条规律也一样。XLM-R-large 的 token F0.5 漂亮得多（0.1 档 0.889 vs mBERT 0.6965），可它的任务质量同样没赢过原文（0.1 档 −0.0022，区间跨零）。代理指标好看，不等于任务更好——这正是 The Token Company 调研留下的教训，也是我们把任务级质量设成主判据的理由。

0.4 档：压缩率还在涨、fact recall 不动、任务质量区间下界为负。该推荐哪个档位？

04判据为什么长成「区间」的样子

先看这 149 条数据长什么样。下面是 0.2 档每条 prompt 的真实差值（压缩后的答案分 − 原文的答案分，judge 打分）：

  • 89 条完全没变（差值 = 0）——大多数时候压缩根本不影响答案；
  • 剩下的 60 条里，有变好的，也有变差的，单条最大涨落到 ±1.0；
  • 149 条算下来，平均差值只有 +0.0009——正负互相抵消，这就是为什么「平均值」这个数如此不可靠。

把均值和区间一起看才有意义。下面这台机器用真实差值现场重采样：每次随机抽 149 条（允许重复），算一个均值，画进直方图。抽得越多，这个分布越清楚，两端 2.5% / 97.5% 分位就构成报告的置信区间。

读法只有三条，值得背下来：

  1. 区间跨过 0 = 看不出差别。0.1–0.3 档的区间都跨 0：不是「变好了」，也不是「变差了」，而是和原文没有可分辨的差别。
  2. 区间整体在 0 以下 = 确实变差。0.4 档 [−0.1075, −0.0279]、0.5 档 [−0.1172, −0.0293] 都整个落在负半轴。这不是噪音，是代价。
  3. 样本量决定分辨力。把样本量切成 45 条或 15 条再看：区间会明显变宽，判据随之失去区分能力——平均值可能一样，结论的强度完全不同。这也是为什么考卷规模是算出来的（按能分出预期效应量倒推），不是拍出来的。

为什么是「配对」重采样？抽的是同一条 prompt 的两个答案之差，从头到尾配对。原文与压缩后的答案来自同一道题、同一个模型，条目之间的差异（题目难度）在配对时被消掉了，剩下的才是压缩真正带来的变化。报告的 RNG 有固定种子（seed 0），所以数字可复现；上面的演示用的是另一套随机数，你会看到略微不同的区间——那正是「要认数字就得认出处」的理由。

把考卷从 149 条缩到 15 条，判据会怎样？

报告写着均值 +0.0095、区间 [−0.0140, +0.0345]。可以对外说「质量略有提升」吗？

05案例：一个数字如何骗人

第 01 课留下一个悬案：mBERT 的 fact recall 五档全部是 0.7699，而事实明明被正则钉死、阈值动不了它。这个案子的查法本身就是「读数字」的示范，四步：

  1. 发现异常。不是「数字不好看」，而是「数字太好了」——一个应该随档位变化的量纹丝不动，说明它测的东西和以为的不一样。
  2. 提出可证伪的假设。「缺口在压缩之后的环节」与「缺口在测量方式本身」，两者都能解释恒定；选后者，因为它能被一行代码验证。
  3. 找独立证据。跑真实前向：#A-1029 解出来是 # A - 1029、12.5% 解出来是 12. 5 %——字符都在，字符串被空格拆开。而判据是字符串包含。
  4. 定量预测并验证。如果假设成立，缺口 ≈ 考卷里「带 ASCII 标点的事实」占比。实测 22.79%，缺口 23.01%。
这一步还没做

这个案子目前只是诊断，没有定案。还差一次 harness 级复核：把比对前的空白归一化，看事实召回率会不会一步跳到接近 1.0。没做之前，任何「我们的模型丢事实」或「考卷测不准」的说法都只是猜想——这正是本课想教的纪律：异常要说出来，结论要标上限。

06读表五问

任何一张 Beam 的数字表拿到手，先问这五句。答不上来就别引用：

  1. 这是哪个口径？计费还是原生？字符串级还是 token 级？
  2. 钉子是什么？作答模型、judge、rubric 版本、harness commit、考卷哈希——有没有和你要比的那份报告一致？
  3. 跟谁比、同档位吗？压缩率是结果不是设定值，不同档位的数字没有可比性。
  4. 是代理指标还是主指标？代理指标用来做日常回归，声称优劣只看任务级质量。
  5. 区间下界多少、样本量多少？均值不带区间就不能上桌。

打印版在 读表五问，与这份课文同源。

07收尾：三句话

记住这三句就够用

  1. 先问口径，再看数字。同一个压缩率有两个值，方向还会随模型翻转。
  2. 代理指标会背离主指标。压缩率在涨、token F0.5 漂亮，任务质量也可能确定地掉。
  3. 均值不带区间就不能上桌。判据是区间下界，样本量决定这个判据有没有分辨力。

不看上文，写一遍

用你自己的话说明：为什么 0.4 档「不值得推荐」，而你手里有哪三个数字能支撑这个说法？

1. 任务质量区间整段在 0 以下——0.4 档 [−0.1075, −0.0279]，主指标确定变差，不是噪音；
2. 压缩率的上涨是代理指标的上涨——0.3590 → 0.4179 只说明省得更多，不说明答得更好；
3. fact recall 恒定 0.7699 不能当挡箭牌——它被正则钉死，对档位不敏感，根本不参与这个判断。
