Beam 学习空间 · 第 01 课

一次压缩调用里发生了什么

Beam 的压缩只有一个动作：让模型给每个 token 打一个「该保留」的概率，低于阈值的删掉。整条压缩链路——档位、事实、分块、蒸馏——都是这一句话的推论。

约 15 分钟 所有数字均为本机实测（可复现，见文末） 配套：术语表 · 压缩管线速查

01先把压缩放回链路里

生产的 refine 是两段：compress（本地 BERT，毫秒级，无网络）和 rewrite（网关的大模型回调，可选）。真正能省下 token 的是第一段；第二段是质量补偿。Beam 的全部工作，就是替换第一段里的那一个 checkpoint 权重——接口、协议、fail-open 语义一概不动。

本课的边界

这 15 分钟只解剖 compress 这一段：从 compress() 收到文本，到吐出压缩文本。它是唯一一处「模型在做决策」的地方，也是最值得先弄懂的机器。

02五步解剖

生产实现是 tokencamp-pro/sidecars/refine/compressor.py，不到 300 行。核心路径只有下面这些，逐行对应：

  1. 分词，顺带取字符偏移。fast tokenizer 把文本切成 subword，并给出每个 token 在原串里的字符区间（return_offsets_mapping）。偏移是第 4 步定位事实的坐标系。 compressor.py:153
  2. 前向一次。BertForTokenClassification 输出 (1, seq_len, 2) 的 logits——每个 token 两个分数：drop / keep。双向编码器意味着第 300 个 token 也「看得见」第 3 个 token。 compressor.py:159–161
  3. 取第 1 列的概率。对两列做 softmax，取 [:, :, 1]，得到每个 token 的 p(keep)。注意：这不是「重要度打分」，而是一个二分类概率——模型回答的问题不是「这个词多重要」，而是「教师模型在这个位置会不会删掉它」。 compressor.py:164
  4. 三处强制置 1.0。[CLS]/[SEP]、命中 _FACT_PATTERN 的 token、<tc_keep> 保护段覆盖的 token——把它们保留概率直接写成 1.0，任何阈值都删不掉。 compressor.py:167–191
  5. 比阈值，然后解码。阈值就是「档位」本身；保留下来的 token id 交给 tokenizer 拼回文本。 compressor.py:194–195, 218 
# sidecars/refine/compressor.py —— 第 4、5 步的原文
threshold = aggressiveness            # 档位就是阈值，不是比例
keep_mask = probs >= threshold        # 逐 token 比较
kept_ids  = inputs["input_ids"][0][keep_mask]
compressed_text = self.tokenizer.decode(kept_ids, skip_special_tokens=True)

为什么是二分类而不是打分排序？因为抽取式压缩天然是「留 / 删」的二值决策。LLMLingua-2 论文把提示压缩形式化为 token 分类问题，正是为了让输出保证是输入的子序列——见文末主读物。

删掉的是 token，不是词。中文在 mBERT 里几乎一字一 token，英文单词则常被切成 chur + ##n 这样的片段——每个片段各自有概率、各自独立生死。这个细节会在第 7 节咬人。

03亲手走一遍（真实前向）

下面这张图不是示意，是本机把生产 checkpoint 的一次真实前向导出成的：每个方框是一个 token，框里是它在原文里的字样，框下是模型给它的 p(keep)。点档位，看谁生谁死。

数据：生产 checkpoint llmlingua-2-bert-base-multilingual-cased-meetingbank，单句、无分块（56 个 token，含两个特殊 token），未启用 min_tokens / max_tokens——与生产默认路径一致。

三件值得盯着看的事：

  • 边界很清楚。你 0.15、是 0.20、如 0.06、请 0.02、两个逗号 0.04 / 0.01——功能词和标点几乎注定被删；退 0.98、款 0.98、订 0.96、单 0.95——实词几乎注定保留。压缩后的文本读起来像电报体，正是因为标点被系统性地删掉了。
  • 0.3 档和 0.4 档的保留数完全一样（40/56）。阈值是连续值，但 token 的概率分布是散的：0.3 到 0.4 之间这段区间里没有任何 token 落着，于是抬档位什么也没发生。改档位不等于改结果。
  • 事实被钉住。#A-1029 与 3 的每个字符都是 1.00（带红框），从 0.1 到 0.5 一动不动。

04档位不是比例

这是最容易记错的一件事：aggressiveness = 0.2 不是「压掉 20%」，而是「保留概率低于 0.2 的全删掉」。它是一个绝对概率门槛，压缩率是它作用在这批 token 上的结果——由文本内容、模型校准共同决定，事前不可知。

本课英文例句（39 token）23.1%25.6%30.8%30.8%33.3%
冻结考卷 149 条（mBERT，计费口径）22.0%29.5%35.9%41.8%47.5%

考卷一行来自冻结基线 docs/evaluation.md（2026-09-12 双 checkpoint 全量）；前两行是本机按生产代码路径实测。三行同一个档位，三个不同的压缩率。

推论有三条，一条比一条重要：

  1. 压缩率不是可指定的输入。想「压到 30%」只能扫档位去找，不能填一个数字要求它。
  2. 同档位才能比模型。换模型会换校准曲线——公开 XLM-R-large 在 0.1 档保留率 0.790，同档 mBERT 是 0.780，同样的代码、同样的阈值，出来的比例就是不一样。所以验收标准写的是「同档 aggressiveness 对比」，测的是「同档不同模型」。
  3. fact recall 在五档上完全没动：mBERT 五档全是 0.7699。阈值管不到它——事实被正则钉死了。既然如此，缺的那 23% 是从哪儿漏的？第 7 节回答。

把档位从 0.2 调到 0.4，压缩率会随之变成 40% 吗？

05两把免死金牌

模型的口味再好也不能全信——数字和编号一旦被删，下游就会拿着残缺的事实回答用户。所以有两处机制绕过概率、直接钉死内容：

_FACT_PATTERN = re.compile(r"#[\w-]+|\d+(?:[.,:/-]\d+)*%?")   # refiner.py:78

它抓的是订单号（#A-1029）、日期、版本、百分比、带千分位或小数点的数字。判定用的是字符区间重叠：token 的字符跨度只要和事实跨度有任何交叠，它的 p(keep) 就被写成 1.0——阈值在 [0,1] 内取任何值都删不掉它。

第二把是 <tc_keep>…</tc_keep>：客户自己标记「这段别动」的内容，语义与数字事实完全相同。有一条防滥用上限——受保护内容最多占输入的 50%，否则把整段 prompt 包起来就等于关掉压缩。

同一个正则，两处使用

评测 harness 里的 fact recall 用的是逐字复制的同一个正则（src/beam/quality.py:33）。两侧必须同时漂移，否则「运行时的安全性」和「考卷上的分数」就变成两把不同的尺子。

钉死不是万能的，两个已知破口写在代码注释里：max_tokens 是硬上限，截断时可能把尾部的受保护 token 一起切掉；分块路径（下一节）里，事实可能因为句子被重新拼接而匹配不上。安全网有洞，洞也被记录在案。

06超过 512 个 token：分块

BERT 的输入窗口是 512 个 token，这是硬限制。所以 compress() 先数一遍：装得下就一次前向，装不下就按句边界把文本打包成每块不超过 480 token 的块，逐块压缩，最后用单个空格把各块拼起来。

  • 阈值按块生效。每块各有一批自己的 token、自己的概率分布，于是每块的保留率各不相同。整篇的压缩率是各块的加权平均，不是一个统一决定的结果。
  • 块与块互不可见。第 3 块的模型看不到第 1 块。跨块的长距离依赖（「上文提到的那个订单」和它的编号）在压缩阶段就是断的——这是这套架构的真实代价，不是实现瑕疵。
  • 用空格 join，原始结构丢失。原文里的换行、缩进、消息边界，压缩后全部塌成单空格。对下游大模型通常无所谓，对依赖格式的 system prompt 可能不是。

07现场诊断：0.7699 是怎么来的

第 4 节留了一个悬念：事实明明被正则钉死，为什么 mBERT 的 fact recall 是 0.7699，而且五档一动不动？本课实测给出了一个非常具体的答案。

看第 3 节里那条英文压缩输出：原文是 12.5%，压缩后是 12. 5 %。中文例句里也一样：#A-1029 变成 # A - 1029。每个字符都活着，但字符串被空格拆开了。

而 fact recall 的判据是字符串包含：fact_recall(item.prompt, result.refined_text)，逐字判断 "#A-1029" in 压缩文本（src/beam/runner.py:277）。空格一插，逐字判定立刻失败——尽管一个字符都没丢。

为什么偏偏是 mBERT？WordPiece 的解码规则是：## 开头的片段粘到前一个 token 上，其他每个 token 前面补一个空格。#、-、.、% 在 WordPiece 里都是独立 token 且不以 ## 开头，于是空格被挨个补进来。XLM-R 用的是 SentencePiece，解出来的就是 #A-1029、12.5%，一个字不差。

这不是事后编的解释，它可以被算出来。冻结考卷的 149 条里，逐条统计「会被解码空格拆开的事实」占比：

量数字来源
考卷里含 ASCII 标点的事实占比（逐条平均）22.79%本机统计 eval/golden/ 149 条
实测 fact recall 的缺口（1 − 0.7699）23.01%冻结基线 docs/evaluation.md
XLM-R-large 五档 fact recall1.0000同上（SentencePiece 不插空格）

22.79% 与 23.01%——两个来源完全独立的数字，量级吻合到小数点后一位。也就是说：mBERT 的 fact recall 缺口，很可能不是模型把事实弄丢了，而是解码把事实拆开了，考卷的比对方式没认出来。

这是诊断，不是定论

要定案还差一步 harness 级复核：把比对前的空白归一化，或者改成按 token 生存率而不是字符串包含来测。这件事的结论会影响「哪些事实真的会丢」——值得单开一课，也值得在仓库里留一条记录。运行时的 guardrail 不受这个现象影响：它比的是 rewrite 之后的自然语言，不是 token 解码的产物。

顺带一个反向证据，同一次实测里抓到的：XLM-R 在 0.1 档把原文的 driven mainly 解成了 drivenly——mainly 被切成两片，main 被杀、ly 活着，解码时粘到了前一个词上。「输出是输入的子序列」这个保证活在 token 层面，不活在字符串层面。它可以拼出一个原文里根本不存在的词。这句话值一整课。

08模型的「口味」从哪来

到这里还剩最后一个问题：模型凭什么知道 enterprise 该留、However 该删？它不是被教会了「什么重要」这个概念，而是被教会了模仿一个教师模型的删改习惯。LLMLingua-2 的数据蒸馏管线，五步：

  1. 切块。语料按 512 token 上限切开——和运行时的分块同源。
  2. 教师压缩。用固定 prompt 让 GPT-4 级模型做只删不改的抽取式压缩（「只能删不重要的词、不许改词序、不许改词、不许缩写」）。
  3. 滑窗模糊匹配。把教师输出里的词逐个对回原文，找出它保留了原文的哪些位置——得到逐词的 keep/drop 标签。这一步是启发式，必然有对不齐的地方。
  4. 质控。丢掉波动最大的 5%（Variation Rate：教师输出了原文里找不到的词，疑似幻觉）和对齐最差的 10%（Alignment Gap：匹配器认不回来的标签）。
  5. 微调。用这份标签数据集训练一个双向编码器 + 分类头——就是运行时的那个 checkpoint。

管线在本仓的实现：src/beam/distill.py（分块 chunk_text、匹配 match_labels、质控 quality_control），策略与红线见 docs/data-strategy.md。

Beam 自己做的是第 2 步的替换：语料不照抄论文——公开语料打底，加上合成的 system prompt 与多轮对话（公开数据集对这两类覆盖不足），并且有两条硬红线：教师的训练集 MeetingBank 一律排除（混进来等于评测时背答案），客户 prompt 永远不进训练与评测。

09收尾：三句话

记住这三句就够用

  1. 概率 → 阈值 → 子序列。模型给每个 token 一个保留概率，低于档位的删掉，输出是输入的 token 子序列。
  2. 档位是概率，不是比例。压缩率是结果，随文本和模型校准浮动；同档位才能比模型。
  3. 事实与保护段被钉死，其余全看模型口味。剩下的缺口多半出在解码与分块这些非模型环节。

不看上文，写一遍

合上这一页之前，用自己的话把五步写下来。写不出第 4 步就回去看第 2 节——这种「努力想一下」的检索，比再读一遍记得牢得多。

1. 分词 + 取字符偏移（偏移留给事实定位用）；
2. 前向一次，得到每个 token 的两个 logits；
3. softmax 取第 1 列，得到 p(keep)；
4. 三处强制 1.0：特殊 token、事实正则命中、<tc_keep> 保护段；
5. 与档位比较并解码：p >= aggressiveness 的 token 拼回文本。
